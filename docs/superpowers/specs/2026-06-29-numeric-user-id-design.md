# Numeric User ID Design

Date: 2026-06-29

## Goal

Change Nano Chat's user identifier from UUID to numeric 64-bit `uid` while keeping JSON `user_id` values encoded as strings, for example `"123456"`. The project is still in development, so this change updates the initial schema directly and does not preserve existing database data.

## Scope

In scope:

- `users.user_id` becomes a PostgreSQL `bigint` identity primary key.
- Every persisted user foreign key becomes `bigint`:
  - `clients.user_id`
  - `conversations.created_by`
  - `direct_conversation_pairs.user_low`
  - `direct_conversation_pairs.user_high`
  - `conversation_members.user_id`
  - `conversation_member_spans.user_id`
  - `messages.sender_user_id`
- Rust service code uses a dedicated `UserId` type rather than raw UUID for user identifiers.
- JSON serializes and deserializes user IDs as strings to avoid JavaScript 64-bit integer precision loss.
- JWT `sub` stores the numeric user ID as a decimal string.
- API docs, Web TypeScript types/tests, and backend tests are updated for numeric user IDs.

Out of scope:

- Existing data migration from UUID users to numeric users.
- Changing `client_id`, `conversation_id`, `message_id`, `span_id`, realtime `connection_id`, or app instance IDs; these remain UUIDs.
- Snowflake-style distributed ID generation.

## Design

Postgres generates user IDs with `generated by default as identity`. Registration inserts users without supplying `user_id` and reads the generated ID from `returning user_id`. This keeps ID generation local to the database and avoids introducing distributed ID generator configuration.

Rust adds a small user ID module/interface that hides JSON details from callers. Internally, user IDs are numeric `i64`. Serde serialization emits decimal strings; deserialization accepts decimal strings and rejects malformed or non-positive values. This gives the backend type safety while preserving a frontend-safe JSON contract.

All existing UUID IDs for non-user entities continue to use the existing UUID v7 helper. Ordering logic for direct conversation pairs continues to compare numeric user IDs, preserving the one-direct-conversation-per-user-pair invariant.

## API and Realtime Contract

Response payloads continue to use the field name `user_id`, but the value changes from a UUID string to a decimal string:

```json
{
  "user_id": "123456",
  "username": "alice",
  "display_name": "Alice"
}
```

Request payloads that reference users also send decimal strings:

```json
{
  "member_ids": ["123456", "123457"]
}
```

This applies to HTTP and WebSocket payloads, including group member operations, direct-message target user IDs, read-update events, member-left events, and dissolved-conversation events.

## Error Handling

Malformed user ID strings in JSON requests fail request parsing as invalid input. Invalid JWT subjects fail authentication with `InvalidToken`, as today. References to syntactically valid but missing users continue to return the existing not-found or authorization errors from service logic.

## Testing

Backend tests should cover:

- Registration returns a decimal-string `user_id` and JWT `sub` authenticates correctly.
- Login with a reused `client_id` still verifies the numeric owner `user_id`.
- Group member, direct message, realtime notify, and visibility-span paths work with numeric user IDs.
- Malformed user IDs in request JSON are rejected.

Web tests should cover:

- Type fixtures use decimal-string `user_id` values.
- Avatar/color stability remains based on the string user ID.
- Realtime event handling still compares `user_id` as a string.

## Rollout

Because existing data is not preserved, developers should recreate the database or rerun migrations from scratch after this change. No compatibility layer for old UUID user IDs is required.
