# Nano Chat Backend v1 Design

Date: 2026-06-13

## 1. Purpose

Nano Chat v1 is a small, production-shaped chat backend. It should be easy to deploy, run as one service binary, and still support multiple service instances for load sharing and rolling upgrades.

The backend provides:

- username/password authentication;
- WebSocket realtime messaging;
- direct conversations and group conversations;
- multi-client login for the same user;
- durable message history in Postgres;
- client-side recovery through sequence-based synchronization;
- cross-instance realtime fan-out through Postgres `LISTEN/NOTIFY`.

The project glossary lives in `CONTEXT.md`. Architectural decision records live in `docs/adr/`.

## 2. Goals and Non-goals

### Goals

- Provide a small but complete IM backend.
- Use Rust with Axum and Tokio.
- Use Postgres as the only required middleware in v1.
- Support multiple service instances behind a non-sticky load balancer.
- Keep WebSocket delivery best-effort while preserving correctness through persisted history and explicit synchronization.
- Keep the public API and WebSocket protocol simple, documented, and versioned.

### Non-goals

- No channels, public rooms, announcement channels, or generic realtime pub/sub platform.
- No Redis requirement in v1.
- No delivery receipts per recipient/client.
- No message delete, edit, recall, media, files, reactions, replies, or typing indicator.
- No friends, contacts, block list, invitation approval, admin backend, user deletion, or account disabling.
- No public online status or persisted `last_seen` / `last_online_at`.
- No OpenAPI generation requirement in v1; maintain a hand-written protocol document instead.

## 3. Architecture

### Runtime shape

One Rust service process provides:

- HTTP REST API;
- WebSocket endpoint;
- local connection registry;
- Postgres connection pool;
- Postgres `LISTEN/NOTIFY` listener;
- graceful shutdown/draining logic;
- optional metrics endpoint.

Multiple identical instances may run concurrently. They share Postgres and communicate realtime events through one Postgres notify channel, for example `nano_chat_events`.

There is no requirement for sticky sessions. A user's clients and connections may be spread across service instances.

### Code organization

Use light layering plus domain modules:

```text
src/
  main.rs
  app.rs
  config.rs
  http/
  ws/
  auth/
  users/
  conversations/
  messages/
  realtime/
  db/
```

Guidelines:

- `auth` owns registration, login, password hashing, JWT validation, and client issuance.
- `users` owns user lookup and profile update.
- `conversations` owns direct/group conversation rules, membership, visibility spans, read positions, and conversation lists.
- `messages` owns message sending, idempotency, sequence allocation, and message history queries.
- `realtime` owns connection registration, heartbeat/idle timeout, local fan-out, and the Postgres notify bridge.
- HTTP and WS handlers should be thin and call domain services.

## 4. Technology Choices

- Language/runtime: Rust + Tokio.
- HTTP/WebSocket framework: Axum.
- Database: Postgres.
- Database access: SQLx with hand-written SQL and migrations.
- Password hashing: Argon2id.
- Entity IDs: UUID v7 for users, clients, conversations, messages, and connections where persisted/exposed.
- External JSON naming: `snake_case`.
- External time format: RFC3339 UTC strings.
- Database time type: `timestamptz`.

## 5. Identity, Authentication, and Clients

### Users

- Registration uses `username + password`.
- `username` is globally unique, lowercased at registration, immutable, and used for login and exact lookup.
- `display_name` is optional and mutable.
- If `display_name` is empty, clients display `username`.
- No email, phone, OAuth, password reset, user deletion, or user disabling in v1.

Validation:

- `username`: 3-32 characters; lowercase letters, digits, and underscore only.
- `password`: 8-128 characters.
- `display_name`: optional, 1-80 characters when present.

### Passwords and tokens

- Store password hashes with Argon2id.
- Login returns a JWT access token valid for 7 days.
- JWT subject is `user_id`.
- `JWT_SECRET` comes from environment configuration.
- No refresh token and no server-side token revocation in v1.
- Logout is local: the client deletes its token and closes active WebSocket connections.
- A WebSocket connection validates the token at connection time. The connection is not closed merely because the token expires later.

### Clients and connections

A user may have multiple clients. A client is a stable logged-in instance, such as a browser profile or mobile app install.

- `client_id` is generated by the server as UUID v7.
- Login may include an existing `client_id`.
- If the supplied `client_id` belongs to the user, reuse it.
- If the supplied `client_id` is missing, create a new client.
- If the supplied `client_id` is invalid or belongs to another user, return an error.
- Each successful login returns a fresh access token and the effective `client_id`.
- v1 does not expose client management APIs.

A connection is an active WebSocket link for one authenticated client.

- Connection state is instance-local memory only.
- Do not persist connection state in Postgres.
- Do not maintain a global connection registry in v1.
- Limit each user to at most 10 simultaneous online connections.
- The same `client_id` may have multiple simultaneous connections, such as multiple browser tabs.
- Realtime fan-out is connection-based: each relevant connection receives events, except the origin connection for commands that already receive an explicit OK response.

## 6. Conversations

v1 has two conversation types:

- direct conversation;
- group conversation.

There are no channels in v1.

### Direct conversations

- A direct conversation has exactly two users.
- Each pair of users has at most one direct conversation.
- Direct conversations are not created as empty conversations.
- The first direct message is an atomic operation: create or reuse the direct conversation, then insert the first message in the same transaction.
- Direct conversations cannot be exited, dissolved, hidden, or deleted in v1.
- A direct conversation appears in the conversation list only after it has at least one message.

### Group conversations

A group conversation is defined by its named, managed membership model, not by current member count. A group may start with two active members and may later have one active member; it becomes dissolved only when the last active member leaves.

- A group conversation has a required name, 1-80 characters.
- Group names are not globally unique.
- Creating a group requires creator + at least one other initial member.
- The creator automatically becomes an active member.
- A group appears in active members' conversation lists immediately after creation, even if it has no messages.
- Any active group member may add another user.
- Adding a member directly joins the user; there is no pending invitation or acceptance flow.
- Active group member limit is 500.
- The limit applies only to currently active members, not historical members or visibility-span records.
- Only active members may send group messages or add members.
- Members may leave a group.
- A former member may be added again.
- If the last active member leaves, the group becomes dissolved.

### Dissolved groups

A dissolved group:

- has no active members;
- cannot receive new messages;
- cannot have members added;
- cannot be reactivated in v1;
- keeps message history and visibility spans;
- can still be read by former members within their visible ranges;
- is not shown in the default conversation list.

## 7. Membership and Visibility

Group membership has active and historical states. A former member may have readable history without being active.

Use visibility spans to represent message history access. A visibility span is a contiguous range of conversation-local message sequences visible to a user.

Rules:

- Direct conversation members can read from sequence 1 onward.
- A user's first join to a group creates a visible range starting at sequence 1, so new members can see existing group history.
- Leaving a group closes the current open visible range at the group's current latest message sequence.
- Rejoining a group opens a new visible range starting at `latest_message_seq + 1` at the time of rejoin.
- Messages created while the user was out of the group are not visible to that user.
- Historical queries must filter by the user's visible spans.

Example:

- User joins while latest seq is 0: visible from 1.
- User leaves at seq 10: visible range 1-10.
- Group receives seq 11-20 while user is absent.
- User rejoins when latest seq is 20: new visible range starts at 21.
- User can read 1-10 and 21+, not 11-20.

## 8. Messages

### Message model

v1 supports only text messages.

- Text body must be non-empty after trim.
- Store the original body, including whitespace and newlines.
- Maximum body size is 4096 UTF-8 bytes.
- Messages are immutable after creation.
- No message delete, recall, edit, attachments, images, files, reactions, replies, or rich media in v1.
- Message history contains only user-sent messages, not membership/read/system events.
- Sender display data is not snapshotted in the message table; messages store `sender_id` and APIs join current user summary.

Each message has:

- `message_id` UUID v7;
- `conversation_id`;
- `message_seq` scoped to the conversation;
- `sender_user_id`;
- `client_id`;
- `client_msg_id`;
- body;
- created timestamp.

### Sequence allocation

Messages are ordered within a conversation by `message_seq`, not by timestamp.

To send a message:

1. Start a transaction.
2. Lock the conversation row with `SELECT ... FOR UPDATE`.
3. Validate conversation state and sender permissions.
4. Validate idempotency key.
5. Increment `conversations.last_message_seq`.
6. Insert the message with the new sequence.
7. Update conversation last-message metadata.
8. Update sender read position so the sender's own message does not count as unread.
9. Commit.
10. Publish the realtime event through Postgres `NOTIFY`.

This serializes sends within one conversation. It is acceptable for v1.

### Send success semantics

Database history is the source of truth.

- A send succeeds only after the message is persisted.
- WebSocket realtime push is best-effort acceleration.
- If persistence fails, the send fails.
- If persistence succeeds but realtime delivery fails or is missed, clients recover through synchronization.

### Idempotency

Every send command must include `client_msg_id`.

- Scope: `(sender_user_id, client_id, client_msg_id)`.
- The client generates it; recommended UUID/ULID, but not strictly required.
- It must be a non-empty short string, length 1-100.
- Same key + same request returns the existing message.
- Same key + different request returns `idempotency_conflict` and creates no message.
- The server stores enough request fingerprint data to detect conflicts, including target conversation/direct target and body hash.

## 9. Read Positions and Unread Counts

Each user has a user-level read position per conversation.

`read_seq` is an unread watermark, not proof that every sequence number was actually visible/read. Visible messages at or below `read_seq` do not count as unread.

Rules:

- Read positions are user-level, not client-level.
- Any client updating read position updates the user's state across all clients.
- `read_seq` only moves forward.
- If a client requests a backwards update, keep the existing value.
- If a client requests a value beyond its allowed readable/current range, return an error.
- When a user sends a message, the sender's `read_seq` advances at least to that message's `message_seq`.
- When a user rejoins a group after absence, advance that user's `read_seq` to the group's current latest sequence so invisible absence messages do not count as unread.
- Unread counts consider only visible user-sent messages newer than `read_seq`.
- Conversation events do not count as unread messages.

## 10. Synchronization and Pagination

WebSocket does not replay history on connect. Clients recover by HTTP synchronization.

Startup/reconnect flow:

1. Open WebSocket for realtime events.
2. Fetch `GET /api/v1/conversations`.
3. Compare local conversation state with returned latest sequences/read positions.
4. For conversations with gaps, fetch messages by sequence cursor.

Message pagination uses sequence cursors, not offsets.

- Fetch newer: `after_seq=123&limit=50`.
- Fetch older: `before_seq=123&limit=50`.
- Default `limit`: 50.
- Maximum `limit`: 100.

If a client receives a realtime `message.created` event with a sequence gap:

1. Temporarily buffer the out-of-order event.
2. Fetch missing messages from HTTP using `after_seq`.
3. Apply messages in sequence order.
4. Treat HTTP history as authoritative if it disagrees with the buffered event.

## 11. Conversation Lists and Member Lists

The default conversation list is the user's current active chat entry list.

It includes:

- direct conversations that have at least one message;
- group conversations where the user is an active member, including groups with no messages.

It excludes:

- direct conversations with no messages;
- groups the user left;
- dissolved groups.

A separate archive/history list is not part of v1. If a client already knows a conversation ID, former members may still fetch visible historical messages where permitted.

Conversation list items include summaries only:

- conversation id;
- conversation type;
- group name for groups;
- direct counterpart user summary for direct conversations;
- latest message summary when present;
- latest message sequence;
- user's read sequence;
- unread count;
- active member count for groups.

The conversation list does not inline full group member lists.

Member list API:

- Group member lists show active members only.
- Historical/former members are not listed in v1.
- Historical messages still include sender summaries through current user data.

## 12. Realtime Transport and Protocol

### Transport

v1 uses WebSocket for realtime client transport.

Alternatives considered:

- SSE + HTTP POST is simpler for one-way push but worse for bidirectional chat commands.
- WebTransport is promising but more complex to deploy and not needed for text chat v1.
- MQTT and WebRTC add unnecessary protocol/product complexity for this backend.

### Versioning

- HTTP paths are under `/api/v1`.
- WebSocket endpoint uses a version parameter, for example `/ws?version=1`.
- Unsupported versions are rejected during connection.

### Envelope

All WebSocket messages use a common envelope with `snake_case` JSON.

Command example:

```json
{
  "id": "request-123",
  "type": "message.send",
  "payload": {
    "conversation_id": "...",
    "client_msg_id": "...",
    "body": "hello"
  }
}
```

Success response example:

```json
{
  "id": "request-123",
  "type": "message.send.ok",
  "payload": {
    "message": { }
  }
}
```

Event example:

```json
{
  "type": "message.created",
  "payload": { }
}
```

Error example:

```json
{
  "id": "request-123",
  "type": "error",
  "error": {
    "code": "conversation_not_found",
    "message": "Conversation was not found"
  }
}
```

Heartbeat messages use the same envelope and may omit `id`.

### Client commands

v1 WebSocket commands:

- `message.send`: send text to an existing conversation.
- `direct_message.send`: send text to a user by `user_id` or exact `username`, creating/reusing the direct conversation atomically.
- `conversation.read`: advance read position.
- `heartbeat.ping`: application-level heartbeat.

HTTP does not expose public send-message endpoints in v1.

### Realtime events

v1 realtime events:

- `message.created`;
- `conversation.read_updated`;
- `conversation.member_added`;
- `conversation.member_left`;
- `conversation.dissolved`;
- `heartbeat.pong`.

No typing, presence, delivered, edited, deleted, or media events in v1.

### Origin echo behavior

Each service instance has an `instance_id`. Each WebSocket connection has a `connection_id`.

Cross-instance realtime events carry:

- `origin_instance_id`;
- optional `origin_connection_id`.

The connection that sent a command receives a `*.ok` response and does not receive a duplicate event for the same action. Other relevant connections, including the same user's other tabs/devices, receive the event.

### Event fan-out rules

- `message.created`: send to all relevant online connections for users who can see the message, except the origin connection.
- `conversation.read_updated`: send to active members of the conversation, including the reader's other connections, except the origin connection.
- `conversation.member_added`: send to all active members after the add, including the new member, except the origin connection.
- `conversation.member_left`: send to remaining active members plus the leaving user's other connections, except the origin connection.
- `conversation.dissolved`: send to the final leaving user's other connections, except the origin connection.

Business errors do not close the WebSocket. Protocol errors, authentication failure, unsupported version, oversized payloads, and heartbeat timeout close the connection.

## 13. Heartbeat and Connection Cleanup

v1 uses client application-level heartbeat plus server idle timeout.

- Client sends `heartbeat.ping` every about 30 seconds.
- Server updates `last_seen_at` on any valid incoming WebSocket message, including heartbeat.
- Server may return `heartbeat.pong` with `server_time`.
- Each instance periodically scans its local connection registry, for example every 15 seconds.
- If a connection has no inbound activity for 90 seconds, close it.
- Clients reconnect after close and recover missed messages through HTTP synchronization.

The server does not persist user `last_seen` or expose online status in v1.

## 14. Cross-instance Realtime Fan-out

Use Postgres `LISTEN/NOTIFY` as recorded in `docs/adr/0001-postgres-notify-for-cross-instance-realtime.md`.

Rules:

- All service instances listen on one global channel, for example `nano_chat_events`.
- Notify payloads include event type, origin metadata, and enough event payload for direct WebSocket delivery when small.
- For v1 text messages, `message.created` notifications may carry the complete event payload, including sender summary and body.
- Payloads must remain under Postgres `NOTIFY` safety limits.
- Future large events should fall back to ID-only hints or a dedicated fan-out backend such as Redis/NATS/Kafka.
- Each instance receives every notification and filters against its local connections.
- Notifications are best-effort; sequence-based synchronization provides correctness.

No sticky sessions are required.

## 15. Graceful Shutdown and Rolling Upgrades

v1 supports rolling upgrades through draining and client recovery, not seamless connection migration.

On shutdown:

1. Instance fails readiness so the load balancer stops sending new HTTP/WS traffic.
2. Existing requests finish where possible.
3. Existing WebSocket connections receive a `server.draining` event if possible.
4. Connections close.
5. Clients reconnect to another instance and run HTTP synchronization.

WebSocket connections are not moved between processes.

## 16. HTTP API Surface

All endpoints live under `/api/v1` and use JSON.

Authentication:

- `POST /auth/register`
- `POST /auth/login`

Current user:

- `GET /me`
- `PATCH /me` to update `display_name`

Users:

- `GET /users?username={exact_username}` for exact lookup

Conversations:

- `GET /conversations`
- `POST /conversations/groups`
- `GET /conversations/{conversation_id}/messages?after_seq=...&before_seq=...&limit=...`
- `GET /conversations/{conversation_id}/members`
- `POST /conversations/{conversation_id}/members`
- `DELETE /conversations/{conversation_id}/members/me`

Health and operations:

- `GET /healthz`
- `GET /readyz`
- optional `GET /metrics`

No `POST /conversations/direct` because empty direct conversations are not allowed. No HTTP send-message endpoint because sending is WebSocket-only in v1.

## 17. Error Handling

Use stable machine-readable error codes for HTTP and WebSocket.

HTTP uses status codes for broad classes:

- `400`: invalid request shape or validation error;
- `401`: missing/invalid/expired authentication;
- `403`: authenticated but not allowed;
- `404`: resource not found;
- `409`: conflict, such as idempotency conflict or duplicate username;
- `422`: valid request shape but business rule fails.

All errors include:

```json
{
  "error": {
    "code": "stable_machine_code",
    "message": "Human-readable message"
  }
}
```

WS business errors use the same `error.code` vocabulary and do not close the connection.

Important error codes include:

- `invalid_credentials`
- `username_taken`
- `invalid_token`
- `client_not_found`
- `client_owner_mismatch`
- `conversation_not_found`
- `message_not_found`
- `not_conversation_member`
- `not_active_member`
- `conversation_dissolved`
- `group_member_limit_exceeded`
- `message_too_large`
- `empty_message`
- `idempotency_conflict`
- `too_many_connections`
- `unsupported_ws_version`
- `invalid_ws_envelope`

## 18. Database Model Sketch

Tables are intentionally listed as a sketch, not final migrations.

### users

- `user_id uuid primary key`
- `username text unique not null`
- `display_name text null`
- `password_hash text not null`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`

### clients

- `client_id uuid primary key`
- `user_id uuid not null references users`
- `created_at timestamptz not null`
- `last_login_at timestamptz not null`

### conversations

- `conversation_id uuid primary key`
- `type text not null` (`direct` or `group`)
- `name text null` for group name
- `state text not null` (`active` or `dissolved`)
- `last_message_seq bigint not null default 0`
- `last_message_id uuid null`
- `last_message_at timestamptz null`
- `created_by uuid not null references users`
- `created_at timestamptz not null`
- `updated_at timestamptz not null`
- `dissolved_at timestamptz null`

### direct_conversation_pairs

- `conversation_id uuid primary key references conversations`
- `user_low uuid not null references users`
- `user_high uuid not null references users`
- unique `(user_low, user_high)`

This enforces at most one direct conversation per user pair.

### conversation_members

- `conversation_id uuid not null references conversations`
- `user_id uuid not null references users`
- `state text not null` (`active` or `left`)
- `read_seq bigint not null default 0`
- `joined_at timestamptz not null`
- `left_at timestamptz null`
- primary key `(conversation_id, user_id)`

This stores the current member row. Historical readable ranges live in spans.

### conversation_member_spans

- `span_id uuid primary key`
- `conversation_id uuid not null references conversations`
- `user_id uuid not null references users`
- `from_seq bigint not null`
- `to_seq bigint null`
- `created_at timestamptz not null`
- `closed_at timestamptz null`

`to_seq null` means an open span. Queries check whether a message sequence falls within any span where `from_seq <= message_seq` and `(to_seq is null or message_seq <= to_seq)`.

### messages

- `message_id uuid primary key`
- `conversation_id uuid not null references conversations`
- `message_seq bigint not null`
- `sender_user_id uuid not null references users`
- `client_id uuid not null references clients`
- `client_msg_id text not null`
- `body text not null`
- `body_hash text not null`
- `request_fingerprint text not null`
- `created_at timestamptz not null`
- unique `(conversation_id, message_seq)`
- unique `(sender_user_id, client_id, client_msg_id)`

Indexes should support:

- messages by `(conversation_id, message_seq)`;
- conversation list by member and last message metadata;
- active member lookup;
- span visibility filtering.

## 19. Configuration and Deployment

Configuration uses environment variables.

Required:

- `DATABASE_URL`
- `JWT_SECRET`
- `BIND_ADDR`
- `RUST_LOG`

Recommended:

- heartbeat interval/timeout settings;
- max connection limits;
- notify channel name;
- metrics enable flag.

Deployment assets:

- one service image;
- Postgres;
- Docker Compose for local development;
- documentation for running multiple service instances.

Database migrations are explicit.

- Provide SQLx migrations.
- Do not auto-run migrations during service startup.
- Deployment runs migrations as a separate step.
- Service readiness fails if required database access/listener setup is not available.

## 20. Observability

Minimum v1 observability:

- `GET /healthz`: process is alive.
- `GET /readyz`: database is reachable and realtime listener is ready.
- Structured logs/tracing for HTTP requests, WS connection open/close, authentication failures, command failures, message sends, fan-out errors, and shutdown.
- Include request id, user id, client id, connection id, conversation id, and error code where applicable.

Optional but recommended:

- `GET /metrics` in Prometheus format.
- Initial metrics: active connections, WS command counts, messages sent, send errors, Postgres pool state, notify receive count, fan-out failures.

Do not include a Prometheus/Grafana deployment in v1.

## 21. Testing Strategy

Minimum test coverage:

### Unit/service tests

- username validation and login behavior;
- client reuse and ownership validation;
- direct conversation uniqueness;
- group creation rules;
- active member limit 500;
- member leave/rejoin visibility spans;
- dissolved group behavior;
- read position monotonicity and unread calculation;
- idempotent send and idempotency conflict;
- text message validation.

### Database integration tests

- migrations apply cleanly;
- `message_seq` allocation under concurrent sends;
- direct pair uniqueness under race;
- send transaction creates message and updates last sequence atomically;
- visibility-span filtered message queries;
- read position behavior across leave/rejoin gaps;
- unique idempotency constraints.

### HTTP/WS end-to-end tests

- register/login/connect WS;
- send first direct message with `direct_message.send`;
- send to existing conversation with `message.send`;
- multi-client same user fan-out;
- group create/add/leave/rejoin/dissolve;
- read updates across clients;
- reconnect and HTTP synchronization after missed events;
- WS business error does not close connection;
- heartbeat timeout closes idle connection.

### Multi-instance integration test

Start two service instances sharing one Postgres. Connect two clients to different instances. Send a message on one instance and verify the other instance receives the Postgres notification and pushes `message.created` to its local connection. Also verify sequence-gap synchronization remains correct when realtime delivery is skipped.
